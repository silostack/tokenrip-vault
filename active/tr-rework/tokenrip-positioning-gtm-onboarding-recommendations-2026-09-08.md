# Tokenrip: Make shared context the first success and shared ways of working the enduring value

## Executive recommendation

Retain Tokenrip's positioning as a shared workspace that people connect their agents to. Introduce it through a deliberately simple experience: an agent researches the user's business website, saves a business-context file to Tokenrip, and retrieves that file in a fresh conversation. Then show how the same context supports reusable workflows and collaboration across the team.

The strategic sequence is:

**Create useful context → prove it survives the conversation → use it in a workflow → share the way of working → improve it through repeated use.**

The first experience should not carry the burden of demonstrating the entire product. Its job is to create a useful asset, establish a correct mental model, and make the connection trustworthy. The larger value is not recall alone, nor file storage alone. It is the ability to maintain business context, methods, standards, and working artifacts together so that another person or agent can perform work without reconstructing the setup.

Five recommendations follow:

1. **Keep the shared-workspace category.** Explain both shared business understanding and shared methods. Avoid repositioning Tokenrip as a memory utility, storage replacement, or single-purpose content generator.
2. **Make website-to-context-to-fresh-chat the default onboarding.** Require only one connected AI tool. Make dashboard correction, a second tool, and a teammate optional extensions.
3. **Follow recall with one useful workflow.** Supply the method and starter standards; reuse the business context the user just created. A compact company-aware reviewer is the recommended initial candidate, subject to user testing.
4. **Build GTM around people already assembling useful AI workflows.** Attract the person maintaining the setup, deliver individual value first, and expand through a teammate's need to use the same context and method.
5. **Change the homepage's progression more than its category claim.** Show the attainable first success before the fully populated team workspace. Move reusable methods closer to the initial proof; keep richer coordination and automation as expansion.

Confidence is high in the coherence and simplicity of this sequence. Confidence is moderate that it will produce stronger activation and retention than alternative entry points. Commercial differentiation, willingness to pay, and channel performance remain hypotheses. No funnel baseline, acquisition budget, or revenue forecast has been established for this proposal.

## 1. Position the product around a shared working system, not a storage medium

The central customer benefit is that a useful AI setup can become a maintained team capability rather than remain an arrangement inside one person's conversations or local environment.

A business-context document explains the company. A method describes how to perform a task. Standards define what acceptable work looks like. Source materials supply evidence and inputs. Working artifacts record drafts, results, revisions, and decisions. Their composition is more valuable than the independent availability of each file.

For example, a publishing workflow may combine a company brief, topic-selection method, writing guide, editorial standards, and relevant source material. It operates on a draft and saves the resulting work. A teammate can invoke the same maintained setup from another supported harness without rebuilding the dependency list or receiving a lengthy briefing.

This is the distinction between **a shared place to put work** and **a shared way to perform work**. Tokenrip should communicate both, with the latter explaining its broader potential.

### Storage is an implementation choice beneath the value proposition

A future Dropbox or other storage adapter is consistent with this positioning. It would change where some source material lives, not eliminate the need to assemble context, apply methods, manage access, and preserve working relationships.

Cloud-storage products already provide meaningful persistence, sharing, search, and versioning, and some expose agent-accessible operations. Those capabilities should not be denied or treated as the decisive comparison. The strategic question is whether Tokenrip makes a team's maintained context and methods substantially easier to use together across work and people.

An adapter should not create two silently editable authorities for one source. External-source references, imported snapshots, and Tokenrip-owned working artifacts need explicit ownership and update behavior. Storage flexibility is a compatible future direction, not a prerequisite for proving the initial experience.

### The semantic layer should be explained through behavior

On the homepage, “semantic layer” is less useful than concrete consequences:

- An agent can find relevant business context without the user reattaching it.
- A workflow can use several maintained sources for different purposes.
- A teammate can invoke the same method from another connected tool.
- A correction to a standing standard can influence later work.
- A result can retain a record of the sources and versions used to produce it.

This is not a proposal to load every file into every prompt. Methods should declare essential dependencies, while retrieval selects other relevant, permitted material. Company facts, operating instructions, examples, and task inputs have different authority and should not be treated as interchangeable text.

The execution boundary also matters. In the user-driven model, Tokenrip maintains and serves the shared working system; the user's harness performs the reasoning and follows the workflow. This does not imply a centrally executing, deterministic orchestration engine for every task or identical behavior across models.

### “Git for non-code” should remain supporting shorthand

The analogy communicates persistent work, shared history, and continuation across contributors. It should not become the only explanation. Git already handles non-code files, and the phrase can imply branching, merging, approvals, or coordinated multi-file commits that versioned artifacts alone do not guarantee.

The approachable promise is: maintain the context and methods once, keep the resulting work accessible, and let the next person continue. Technical audiences can discover the Git analogy beneath that promise.

## 2. Target a behavior and distinguish the builder from the user

The strongest initial audience is people already using AI for recurring business work and experiencing friction when they reuse or share the setup.

Useful qualifying behaviors include maintaining instruction files, repeatedly supplying company context, generating documents or datasets, correcting recurring output mistakes, and helping colleagues reproduce a good workflow. The audience need not be restricted to a two-founder company, but that situation is a clear instance of the problem.

Two roles drive adoption:

| Role | Immediate need | Reason to adopt |
|---|---|---|
| Builder or internal AI enabler | Turn an effective personal setup into a maintained capability | Stop distributing prompts, context copies, and procedural explanations separately |
| Teammate or operator | Perform the task using the team's established approach | Obtain useful results without assembling or maintaining the system |

A single person can occupy both roles. Single-player value is therefore a legitimate starting point, not a compromise of the team thesis.

The initial buyer hypothesis is the person who owns repeated workflow friction or enables others to work with AI. Broad enthusiasm for AI is insufficient qualification. A user who wants one isolated answer has little reason to maintain a separate shared workspace.

The strategy should not require users to abandon their preferred harness. However, portability claims must follow verified support. Text-based, low-dependency workflows are better initial candidates than workflows that require local file access, specialist tools, or external publishing credentials.

## 3. Use a simple first proof rather than an elaborate demonstration

Several onboarding directions can express parts of the product. They should be evaluated against time to understandable value, setup burden, personal relevance, and the reason to return.

| Direction | What it proves well | Main limitation | Recommended role |
|---|---|---|---|
| Shared story or public evolving object | Participation, artifact history, visible contributions | Novelty may attract attention without establishing a useful business habit | Optional campaign or playground, not default onboarding |
| Save and revise a shared file | Identity, persistence, versioning, practical collaboration | Can be interpreted as file management without revealing methods and context composition | Real-work use case and internal validation |
| Store and recall a random fact | A simple cross-conversation read/write loop | Low personal utility and ambiguous differentiation from native memory | Minimal diagnostic, not the primary narrative |
| Research a business and retrieve its saved context | Personal value, inspectable context, cross-conversation continuity | Does not itself establish recurring workflow value | Default onboarding |
| Run a company-aware workflow immediately | Context composition and useful output | More dependencies and a higher initial comprehension burden | Immediate next step after the first proof |
| Package an existing successful AI process | Transfer of the user's own expertise to the team | Requires more input and judgment to separate reusable method from one-off details | Builder-oriented expansion path |

The website-based experience is recommended because it creates a useful, reusable asset with little input. It compresses context creation and product education into the same action. It also leaves the user in a better state for the next task: the company brief already exists.

The trade-off is intentional. Cross-chat retrieval is not the whole differentiation. Treating that limitation as a reason to make onboarding more elaborate would optimize the first experience for architectural completeness rather than user comprehension.

## 4. Make onboarding a guided, verifiable two-conversation experience

The core experience begins after connecting one supported AI tool. Connection instructions should explain the expected result rather than leave the user with an MCP address and no next action.

### Step 1: Create the first useful business-context file

Suggested prompt:

> Research [website URL] and create a concise business context document covering what the company does, who it serves, its offering, and its positioning. Distinguish confirmed information from assumptions. Save it in my Tokenrip workspace and give me the link.

The resulting document should be short enough to inspect. The initial structure should cover the company's offering, audience, customer problem, positioning, and meaningful unknowns, with source information and a research date. An exhaustive company dossier would increase latency and review burden without improving the first proof.

The agent should return a brief summary, the saved-file link, and the next instruction. If several workspaces exist, it should resolve the intended destination rather than silently choose one. Guided setup should handle the workspace and access prerequisites explicitly.

Website-derived context is a draft, not automatically authoritative company doctrine. Public copy can be incomplete or outdated, and an inference about ideal customers is not a confirmed internal policy. The user should be able to correct important details without completing a lengthy intake.

For a missing, inaccessible, or thin website, accept a short company description or existing document. Website research is a convenient default input, not a hard requirement or the product's identity.

Users who already maintain a good company-context file should be able to save or connect that asset directly. The guided path must not require rebuilding useful work or overwrite an existing source merely to complete the demonstration. Experienced users should also retain a direct connection path into their own workflows.

### Step 2: Retrieve the file in a fresh conversation

Suggested prompt:

> Read my business context from Tokenrip and explain what my company does, who it serves, and what makes it different. Include the source link.

The instruction should explicitly name Tokenrip as the source. A generic question about the company leaves room for the agent to answer from native memory, public knowledge, or a fresh web search, obscuring what was demonstrated.

The successful path must include an actual retrieval of the saved artifact. The answer should identify the source; instrumentation should establish that the retrieval happened. If several company-context files match, the agent should clarify rather than improvise an identity.

The user can complete this in a new conversation within the same tool. A second harness and a teammate are optional stronger proofs, not activation prerequisites.

### The first aha is durable, inspectable business context

The intended realization is:

> The context exists outside this conversation, and another connected conversation can use it without receiving the briefing again.

This is more useful than memorizing an arbitrary fact because it creates the foundation for subsequent work. The success is not that the assistant can describe a website; it is that the user now has an accessible, editable source their agents can reuse.

An optional dashboard correction can strengthen the proof. The user changes a detail outside the original chat, then asks a fresh conversation to retrieve it. This makes the source of the new information especially clear. It should remain optional so the default loop stays small.

Do not require a tutorial about files, agents, permissions, and orchestration before this first success. Explain each concept at the moment the user encounters it.

## 5. Explain storage, context, and sharing through the objects the user just created

The onboarding should make four boundaries understandable without turning into product training.

**Where the file lives.** Show that the business-context document is saved in a named Tokenrip workspace, with a link and an editable representation. It is not merely text in the conversation. Future external-storage adapters should be described separately from the storage path actually available at launch.

**How files become context.** Explain that agents retrieve the relevant files, and workflows combine context with instructions and task inputs. Avoid implying that every connected agent automatically knows every file or that connection itself guarantees all future work is recorded.

**How access works.** Display who can read and modify the saved context using the permissions the product actually enforces. Prefer private or explicitly team-scoped onboarding for business data, but verify or implement that behavior before promising it. Connecting an agent should not be presented as granting universal access to the company.

When an agent retrieves a file, its contents enter that agent's processing environment. The explanation should distinguish Tokenrip's storage and access controls from the policies of the chosen AI provider; it should not suggest that granting retrieval access leaves the content confined to storage.

**How context improves.** Distinguish a correction to one output from a change to standing business context or operating standards. Users should be able to choose whether a correction applies only to the current task or becomes guidance for future work.

Sharing should appear as a meaningful extension: invite a teammate or grant another agent the access needed to use this context. The explanation should identify the relevant scope—workspace, artifact, team, or connection—rather than use reassuring but inaccurate language about granular control.

The dashboard's job is to make the working system understandable and adjustable. The harness remains where the user asks for work. A useful dashboard progression is from the saved file, to its history and access, to the context and method associated with a workflow result.

## 6. Follow the first proof with a workflow that reuses the new context

After retrieval succeeds, the next invitation should be: **put this context to work**. Do not ask for the business briefing again.

The initial workflow should require few external dependencies, produce a compact result, and make company-specific behavior easy to evaluate. It should create or update a working artifact in Tokenrip, closing the read/write loop.

### A company-aware reviewer is the recommended first candidate

Tokenrip supplies a review method and starter standards. The user supplies the business context already created and a short piece of work: a customer reply, announcement, post, or document excerpt.

The workflow reviews the work against the context and standards, identifies specific issues, and saves a revised version. This creates a visible comparison and avoids requiring the user to assess a long, wholly generated article.

The choice is based on onboarding properties, not a recommendation to position Tokenrip as a writing product. It uses small text inputs, requires no publishing credentials, and provides an immediate basis for judgment. If users lack relevant material, a clearly labeled sample may demonstrate the mechanism; it must not be presented as their actual work.

The stronger follow-on moment is a transferable improvement. A user adds a standard such as avoiding unsupported numerical benefit claims. On a different input in a fresh conversation, the reviewer applies that standard without the user repeating it.

The realization is now larger:

> The user did not merely correct an answer. The user improved a method that the team can reuse.

### Other workflows test different aspects of the same strategy

- **Opportunity assessment:** Combines business context with an evaluation method and candidate opportunities. Changing a criterion can visibly change a ranking. It demonstrates judgment clearly but needs credible inputs and should not rely on fabricated discoveries.
- **Customer-inquiry handling:** Assesses fit and drafts a response using the same company context. Two related operations make shared context useful without creating a feature parade. External sending should remain a separate authorized action.
- **CSV normalization and validation:** Combines a schema, validation rules, source file, and transformation method. It is a strong internal proof because success is concrete and recurring.
- **Packaging an existing working process:** Helps a builder separate reusable instructions, company context, examples, and task inputs from a successful personal setup. This is a deeper adoption path, not the default first minute.

The CSV example is particularly valuable for internal use. Alek creates a file; Simon requests corrections; replacement attachments circulate. A first improvement gives the file stable identity and history. The more important improvement turns a recurring correction into a maintained schema or validation rule that Alek's agent applies to the next, different file. The benefit moves from recovering work to preventing repeated process failure.

The strongest reusable demo pattern across these candidates is:

**Perform useful work → improve a shared rule or method → apply it to a different input in a fresh context.**

Identical wording across models is not required. Appropriate use of the maintained sources and standards is the relevant proof.

## 7. Acquire builders with concrete evidence, then expand through use

The recommended GTM motion is self-serve entry with selective hands-on observation, followed by team expansion through real work. It should not depend on a large library of modules, a new storage integration, or autonomous background execution before anyone can experience value.

### Acquisition should show a reproducible outcome

The primary proof asset is a short recording of the actual onboarding: research a business, save the context, open a fresh conversation, retrieve the same file. The asset should invite the viewer to reproduce the result with their own business.

A second proof asset should show the next level: a maintained method using that context, followed by a new task benefiting from an updated standard. The two assets answer different questions—how to start and why to keep using the system.

Prioritize three distribution routes initially:

1. **Founder-led demonstrations and targeted conversations.** Show the exact workflow to people already maintaining AI context and instructions. Use their real work to learn where retrieval, setup, and repeated use break down. Simon's technical demonstrations and Alek's audience conversations can support this, with ownership treated as a proposed operating arrangement rather than a committed campaign.
2. **Task-led educational content.** Explain how to reuse company context, share an effective AI method, or stop repeating a spreadsheet correction. Each piece should terminate in the relevant working flow, not a broad product manifesto.
3. **Integration and workflow discovery surfaces.** Publish accurate setup guidance and a small number of verified examples where the target users discover tools. Evaluate listings, communities, and partnerships by qualified activation and reuse, not installation counts alone.

These are priority hypotheses, not claims that a particular channel already converts. Broad paid acquisition should wait for evidence that visitors can complete the core loop and find recurring value. No paid-spend forecast is justified without baseline conversion, retention, and economics.

### Team adoption should follow a useful reason to collaborate

The builder first saves context and obtains a useful result. A teammate then needs the same file, method, or work product. That need creates the invitation.

Do not force a teammate invitation before individual value. Do not require every recipient to configure MCP merely to inspect a deliverable if ordinary viewing can safely provide value. Connection becomes worthwhile when the teammate wants to act through their agent.

This is a plausible expansion mechanism, not automatic virality. Measure whether invited teammates perform useful work and return, rather than treating an invitation or shared link as proof of network effects.

### Hands-on work remains useful without becoming the homepage's primary demand

Concierge assistance can reveal connection friction and workflow gaps. Solution-led deployments can also produce deeper examples. Neither requires making a sales call the default entry for a user who can experience the core loop independently.

Call processing, an inbox, and background automation remain valuable expansion paths. They may prove more retentive for particular users. The recommendation changes the default order of exposure, not the legitimacy of those workflows.

## 8. Retention should come from ongoing work, not repeated recall demonstrations

A business-context file can be useful but static. There is no reason to expect users to return merely to ask what their company does again.

Retention should arise from workflows that repeatedly read and write the shared environment: reviewing a new document, processing another CSV, preparing a customer response, or continuing an existing piece of work. New outputs make the workspace more useful only if they remain findable, appropriately scoped, and connected to relevant methods and sources.

The most promising compounding loop is:

1. A method uses maintained context to produce work.
2. A person reviews the result and identifies a meaningful correction.
3. A standing improvement is explicitly recorded where appropriate.
4. Another task or teammate benefits from the improvement.

Do not assume every edit should become general guidance. Unchecked promotion of exceptions into company policy would make the system less trustworthy over time.

A deeper extension is version-aware dependency tracking. If a shortlist was generated from an earlier dataset, an agent could identify that its source has since changed and offer to refresh the output. This requires actual version-level relationships and freshness behavior; it should not be marketed as automatic until verified.

Lifecycle communication should help a user complete a relevant next task or recover a failed setup. Generic reminders to query the workspace are unlikely to create a habit. Notifications about real shared work can become useful once the workspace has activity and the user has chosen to receive them.

## 9. Monetization should follow demonstrated recurring value

The initial experience must be generous enough to prove creation, retrieval, and meaningful reuse. Charging before the user understands the shared system would increase friction at the weakest point in comprehension.

The working commercial hypothesis is that customers pay for maintained team capability, dependable collaboration, and eventually reduced supervision or background execution—not primarily for storage capacity or a copied prompt.

Workspace-oriented packaging is consistent with a product used by multiple people and agents. However, the exact unit, limits, and upgrade triggers should remain open until repeated use shows what customers value.

Two hypotheses deserve explicit comparison:

- **User-driven use is the entry; automation drives payment.** Customers pay when the system starts handling work without a person opening a harness.
- **Collaboration itself drives payment.** Customers pay because several people can depend on shared methods, context, history, and working state, even when their own harnesses execute every task.

The second hypothesis should not be excluded simply because background execution is a clean conceptual paywall. Neither should it lead to charging for basic safety. Access controls and reliable handling of customer work are product obligations, not optional trust upgrades.

Willingness to pay, support burden, storage and retrieval costs, and conversion from repeated use remain unconfirmed. Pricing numbers, market-size estimates, and revenue projections would add false precision at this stage.

## 10. Keep the homepage category and replace the missing first chapter

The homepage should describe the larger workspace while making the first action immediately achievable. Its current emphasis on a populated, active team environment is useful destination-setting; the recommended onboarding supplies the starting point.

### Preserve the literal hero and add shared methods to the supporting copy

Retain the headline:

> A shared workspace you plug your agents into.

Recommended supporting copy:

> Give your agents the context to understand your business and the instructions to work your way. Keep that context, your workflows, and the work they produce in one workspace your team can use from its existing AI tools.

This retains breadth while naming both business understanding and method reuse. A broader headline rewrite is not necessary to test the new entry point.

### Make the primary invitation about the visitor's business

Recommended CTA concept: **Build your business context.**

Supporting explanation:

> Connect your AI tool, ask it to research your company, and save the context to Tokenrip. Then open a fresh chat and try it.

The action should open the guided path, including connection instructions. Raw MCP and skill-install commands should remain easy to find. A public Tokenrip workspace is useful as an optional example, but it should not be the only route before users can work with their own context.

Avoid unmeasured completion-time promises. “Simple” should be established by successful use, not by describing setup as effortless.

### Use a progressive page structure

| Section | Reader's question | Recommended content |
|---|---|---|
| Hero | What is this, and why connect? | Shared workspace, business context, methods, supported tools, primary action |
| First proof | What can be accomplished immediately? | Website research → saved context → fresh-chat retrieval, with a visible source |
| Context in use | Why is the saved file valuable beyond recall? | One workflow combining business context, a method, and standards to produce work |
| Team continuation | Why does this matter beyond one person? | A teammate invokes the same maintained setup from another supported tool |
| Workspace explanation | Where do files, decisions, and pending work fit? | Concrete objects, their roles, and how users inspect and adjust them |
| Deeper capabilities | What can the system grow into? | Repeated workflows, inbox-driven work, and clearly labeled automation status |
| Get started and FAQ | What happens next, and what are the boundaries? | Two-conversation guidance, storage, access, execution, portability, export |

The first demonstration should match the available onboarding. A richer analytics or cross-team coordination example can remain lower on the page as evidence of expansion.

### Explain composition in one concrete example

Suggested section heading: **Now put that context to work.**

Suggested copy:

> Your company brief explains who you serve. Your writing guide defines the method. Your editorial standards define what good looks like. A workflow uses them together to create and revise a draft.

> Maintain the method in one place. Teammates can use it from their connected agents without assembling the context again.

The example should be visibly a use case, not a narrowing of the product category to content generation. Other task examples can establish breadth without overwhelming the first page.

### Remove absolutes that weaken credibility

Do not argue that chat files disappear when a tab closes, that ordinary folders cannot be shared, or that every competitor is limited to read-only storage. These are unnecessary claims and distract from the actual benefit.

A more durable problem statement is:

> The business context, instructions, and corrections that make one agent useful still need to reach the next conversation or teammate. Tokenrip gives that working setup a shared home.

Also avoid implying that every agent automatically reads every file, every conversation is recorded, or every correction instantly updates all running sessions. Describe actual retrieval, write-back, reload, and sharing behavior. Keep proposed capabilities distinct from live ones.

The office and Git metaphors can remain supporting explanations. Neither should replace the concrete first experience or require repeated defense against the “company brain” category.

## 11. Validate the whole adoption sequence, not merely a successful demo

The product should distinguish four milestones:

| Milestone | Observable evidence | What it does not prove |
|---|---|---|
| Connection | A supported client authenticates and can access the intended workspace | Personal value or willingness to return |
| First proof | A fresh conversation retrieves the business-context artifact created earlier | Differentiation or recurring use |
| Functional activation | A workflow uses that context to create or revise useful work | Team adoption or willingness to pay |
| Durable adoption | Repeated useful work across sessions; method improvements and teammate reuse indicate additional depth | Scalable acquisition economics |

Instrument these separately. A model's assertion that it saved or retrieved something is insufficient; the underlying operation should be observable.

Measure completion and elapsed time by supported harness, connection failures, artifact retrieval correctness, context corrections, transition into a real workflow, and subsequent reuse. Track assisted and unassisted users separately so founder help does not masquerade as self-serve success.

The proposed primary adoption measure is **workspaces performing useful, context-backed work repeatedly across sessions**. Team participation and cross-harness use are important dimensions of depth, but should not exclude valuable single-person use from the initial picture.

### Use evidence gates rather than a speculative calendar

**Gate 1: The first loop works without rescue.** Observe a small initial cohort completing the guided flow on supported harnesses. Include thin websites and ambiguous workspace cases. Ask users to explain where the context lives and how the second conversation obtained it. A small cohort diagnoses friction; it does not establish population conversion rates.

**Gate 2: Recall leads to useful work.** Offer one low-dependency workflow and observe whether users use their context for an actual task. If they stop after the company summary, the first demo may be comprehensible but commercially weak. Improve the bridge to recurring work before adding more traffic.

**Gate 3: Improvements and collaboration transfer.** Run repeated real workflows internally and with early users. For CSV work, check that a saved standard prevents the same problem on a different input. For a reviewer, check that an updated standard influences later work. Observe a teammate using the setup without the builder providing a separate briefing.

**Gate 4: The value survives a fair alternative.** Compare a recurring task against the user's best existing arrangement of shared files and agent instructions. Tokenrip does not need every feature to be exclusive, but it needs a meaningful improvement in setup, maintenance, confidence, or collaboration.

**Gate 5: Expand distribution and test payment.** Only after useful repeat behavior appears should the team increase acquisition effort or harden monetization around the behavior. Set numerical conversion targets after obtaining a baseline; do not invent precise success rates for an unmeasured funnel.

Simon is the proposed owner of runtime correctness, retrieval and write-back instrumentation, and supported-harness verification. Alek is the proposed owner of audience-language feedback and targeted distribution experiments. Both should observe the earliest user sessions. This is a suggested division of responsibility, not a commitment inferred from existing channel performance.

## 12. The strategy rests on five assumptions that should remain explicit

| Assumption | Why it matters | Cheapest disconfirming evidence |
|---|---|---|
| Website-derived context is useful enough to retain | It is the first asset and input to subsequent workflows | Users cannot recognize or use it without extensive rewriting |
| Fresh-chat retrieval creates understanding and trust | It is the initial proof of the shared workspace | Users attribute the answer to ordinary memory or cannot explain the source |
| A simple workflow creates a reason to return | Persistence alone is unlikely to sustain use | Users complete onboarding but perform no subsequent real work |
| Maintained methods reduce repeated setup or corrections | This is the broader differentiation thesis | An existing shared-folder or native setup works equally well with no meaningful burden |
| Builders can bring operators into useful shared work | This is the team-expansion hypothesis | Teammates view outputs but never need or adopt the shared capability |

Important execution risks are bounded but real. MCP connection does not ensure website-browsing capability. A generated local file may need a separate transfer path. Permissions must cover retrieved sources as well as outputs. Stale context can produce confidently wrong work. Source documents must not acquire instruction authority merely by being retrieved. Shared method updates can alter later behavior unexpectedly unless their scope and version are visible.

These risks argue for a small, observable initial path, not a larger onboarding tutorial. Start with text, explicit retrieval, inspectable files, and a low-dependency workflow. Add automation, broader file handling, and more elaborate dependency behavior only when they serve observed use.

## Decision for evaluation

The proposed strategy is to keep the larger shared-workspace ambition while lowering the burden of the first experience. The website-derived business-context file is the entry, not the product ceiling. The second conversation proves that the shared context is real. A reusable workflow proves that the context can do useful work. A teammate or later task benefiting from an improved method proves the longer-term value.

The key evaluation question is not whether a richer demo can display more features. It is whether this sequence makes the product easy to begin, gives users a meaningful reason to return, and leads naturally to a team maintaining its way of working on Tokenrip.

Approval of the direction would endorse that sequence and its validation gates. It would not settle the winning workflow, pricing model, channel economics, or the full technical implementation. Those decisions should follow evidence from the first users and repeated real work.
